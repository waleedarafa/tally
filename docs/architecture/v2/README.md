# Tally decision log, second design

The architecture was designed a second time, from zero, in sixteen steps. The full reasoning, options and rejected alternatives live in the **Tally Design Record**, [`design-record.md`](design-record.md) (a snapshot of the document where it is written, refreshed at the end of every step and slice). This file summarises the decisions the code must follow.

Rules for this log are unchanged from the first run: one decision per record; an accepted decision's text is never edited, only superseded.

First-run records are archived under `docs/architecture/archive/first-run/` as `FR-NNN`. The mapping at the end says what happened to each.

| 032 | Authentication. Every request carries a signed token (JWT) from an identity provider, and Tally checks it. Every later request is checked against that link, so one user cannot read or change another account (I-04). Idempotency keys are scoped per caller, as 027 foresees. Staff in the back office use the same kind of token; their roles are decided with the first back-office endpoint. **Required before production**. **One account for each user** (WAR-84, decided 13 November 2026): the link table holds one row for each user, with a named unique constraint; a second "open an account" from the same user answers 200 with the account the user has. | 033 | The access feed. (1) A billing module, `accessfeed`, listens to `SubscriptionChanged` and `StandingChanged` and keeps one row of current access facts per account, with a sequence that goes up by one only when the facts change. It holds no access rule, and uses the events of `subscription` and `account`, never their APIs: a new, permanent line in the graph (`accessfeed: shared, platform, subscription, account`) that replaces Access's TEMPORARY one. (2) Tally's own relay on the platform queue sends that row to the event log (topic `access-facts`, key = account ID, compacted), not Spring Modulith's externalization, which may let a later event overtake an earlier one, and not change data capture. Its property: for one account, only one send runs at a time, and each send carries the facts current when it starts, so a later send never carries an older sequence. Each send is a Kafka transaction of its own, committed only once the broker has acknowledged the message, and Access reads only committed messages (`read_committed`): a send the broker did not acknowledge can still reach the log later (Slice 2 spike S-4), after a newer one from another instance; in a transaction that is never committed, Access never sees it (decided on the PR-5 pull request). So the managed log (006) must support Kafka transactions, `read_committed`, and the broker's refusal of a late write after an abort; a service that does not is not a candidate, and spike S-4, experiment 3, is the test to run against one. Known limits: an instance that dies between a send and its commit holds committed readers of that partition back for up to the transaction timeout (15 s), once; one producer sends one account per transaction, so an instance sends a few hundred accounts a second at most (enough for sign-ups, not for a backfill of every account). A send holds the account's row lock and one database connection while it calls the log, about 16 s at most with the defaults: the one allowed case of rule 6's "no transaction open during a call out" (CLAUDE.md rule 15). Access applies a message only if its sequence is higher. Assumptions for Slice 2: a subscriber is the account (`GET /v1/access/{subscriberId}` takes the account ID); a value Access does not know never takes access away (an unknown standing is not BLOCKED, a source in an unknown state counts as active), and Access counts each such value; no production database exists, so no backfill of the feed is built. Amends 006 and 012 | Slice 2 brief, decisions 1, 2 and 4, confirmed 13 November 2026 (#60) |
| 034 | The contract between billing and Access. Billing's commit stage fails when a message `accessfeed` can build is invalid against the schema or lacks a field Access reads (F7); Access's tests read every example. Refines 011 | Slice 2 brief, decision 3, confirmed 13 November 2026 (#60) |
| 035 | Access keeps its position in the event log in its own database, in the same transaction as the facts, one position per partition. Access never commits a position to the broker. So an emptied Access database rebuilds from the start with no operator step. | 036 | Access marks its copy "complete once" in its own database, the first time the copy reaches the end of the log that an instance saw at start. An instance that finds the mark at start is ready at once, before it reads the log, so it answers from its copy also while the log is down (D13); the copy may be behind. An emptied database has no mark, so a rebuild stays not ready until it has caught up. | 037 | The Collections case. One case per account covers every unpaid invoice: a decline while a case is open adds the invoice, a retry or "pay now" asks for every unpaid invoice of the case, and the case closes only when none is unpaid. The timetable counts from the case's first decline: a retry on day 3 and another on day 7; OVERDUE one hour after the day-7 retry is asked, day 10 BLOCKED and day 30 WRITTEN_OFF, each only if a debt is still open. Only a decline opens a case (013); after that no payment outcome moves the case forward, since each timer looks only at "is a debt still open", and only `InvoicePaid` moves it back. The hour is D2's measure (an unknown payment is resolved within one hour) and a setting, like the days. No event tells Collections that a retry was declined (spike S-1), and none is added. Collections never moves money: it asks Invoicing. The standing follows the case: the step that changes the case calls `AccountStanding.set` in the same transaction, and the case's version orders a race, so the end state is never "case closed, standing BLOCKED". Each timer is a claimed row on Collections' queue, with a business unique constraint for the step. "Pay now" (`POST /v1/accounts/{accountId}/collections/payment-requests`, with an `Idempotency-Key`) asks again for every unpaid invoice of the case, in any state with a debt open; its decline changes no state. Every request of a case, scheduled or "pay now", takes the next retry number at the moment it is asked (#80, option B), so an early "pay now" changes nothing in the timetable. After a write-off the standing stays BLOCKED until the debt is paid, then GOOD; the subscription stays ended. Any live state → ENDED, by `SubscriptionApi`'s new command (reason `WRITE_OFF` or `FIRST_PAYMENT_DECLINED`; Collections is its one caller), with a new `SubscriptionChanged` type `ENDED` (add only). ENDED refuses everything, a renewal included. One **live** subscription per account (a partial unique index), so an account whose subscription ended can sign up again. | 039 | The identity provider's keys while it is down (Slice 4 spike S-2).
